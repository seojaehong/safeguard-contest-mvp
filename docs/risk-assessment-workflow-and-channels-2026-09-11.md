# SafeClaw 위험성평가 디자인·UX 전면 리팩토링 계획

## 결정 상태

2026-09-11 사용자 요청에 따라 추가 제품 구현·배포는 중지하고 설계를 먼저 확정한다. 아래 내용은 구현 완료 보고가 아니라 승인 전 계획이다. 앞서 진행한 기능 복구 변경은 별도 미커밋 상태로 보존하며, 실행 중이던 검증 결과만 회수한다. 디자인 개편과 묶어 조용히 배포하지 않는다.

목표는 기존 화면을 더 작게 압축하는 것이 아니다. **처음 온 실무자가 작업 정보를 넣고, 위험성평가를 수정·검토한 뒤 파일을 얻는 과정을 이해하고 완료할 수 있는 업무 도구**로 다시 설계한다. 과거 viewport/PASS 산출물은 참고 자료이지 사용자 사용성의 대체 증거가 아니다.

## 디자인 진단

현재 소스와 이번 로컬 실사용 화면에서 확인한 문제를 분리한다.

| 관찰 | 설계상 문제 | 개편 원칙 |
|---|---|---|
| 큰 문서 제목, 전역 메뉴, 문서 런처, 검토 상태, 편집 도구가 동시에 노출 | 하나의 화면에서 무엇을 먼저 해야 하는지 약함 | 작업 단위 제목, 현재 단계, 다음 행동만 최상위에 배치 |
| 모바일 선택 위험 행의 번호·제목·메타정보가 한 줄에서 압축 | 화면 높이 기준을 맞추다가 읽기와 조작을 희생 | 중요 필드 우선, 보조 정보는 상세; 잘림으로 해결하지 않음 |
| 여러 패널의 내부 스크롤과 sticky가 혼재 | 어디가 움직이고 현재 어디에 있는지 불명확 | 데스크톱은 평가표 영역 중심, 모바일은 자연스러운 단일 문서 흐름 |
| 편집 도구/카드/노란 보조 버튼의 시각적 강도가 뒤섞임 | 주요 행동과 보조 행동이 경쟁 | 명확한 기본·보조·위험 동작 체계 |
| 생성된 데이터와 설명 원문을 별도로 동기화 | 생성 직후 편집 잠금, 원문 덮어쓰기 위험 | 구조화 정본과 사용자 원본을 구분하고 표시 문서는 정본에서 파생 |
| 전송 미리보기와 실제 발송 가능 여부가 섞이기 쉬움 | 사용자가 완료 상태를 오해 | 준비·검토·저장·전송 결과를 각각 표현 |

구조적 부담도 확인된다. 현재 `app/globals.css`는 약 678KB, `WorkpackEditor.tsx`는 약 231KB, `SafeGuardCommandCenter.tsx`는 약 122KB다. 파일 크기 자체가 버그 증명은 아니지만, 추가 전역 selector 덮어쓰기보다 책임 분리와 기존 스타일 퇴역 계획이 필요하다.

## 대상 사용자와 기본 여정

우선 설계 대상은 사무실에서 평가표를 작성·검토하는 실무자이며, 모바일 현장 사용자는 작업·사진·확인사항 입력과 항목 검토를 우선한다. 이는 이번 설계의 가정이며 실제 주 사용자 확인 후 조정한다.

기본 여정: **작업 시작 → 작업 정보 확인 → 위험성평가 편집 → 검토·내보내기**.

- 시작은 새 작업과 기존 평가표 가져오기를 구분한다. 가져오기 미구현 기능은 사용 가능한 버튼처럼 노출하지 않는다.
- 장소·작업·인원·장비·조건을 확인하고, AI가 추출한 값과 사용자가 확인한 값을 구분한다.
- 위험성평가표가 중심 문서다. TBM·기록·기타 지원 문서는 평가표 이후 선택 산출물이다.
- 작업 목록은 최근 문서, 진행 상태, 마지막 저장 시각 중심으로 구성한다. 대시보드 숫자 카드나 기능 소개가 첫 화면을 대신하지 않는다.
- 기존 URL은 작업 상태를 가진 새 화면으로 연결하되, 저장본·뒤로가기·새로고침 복원 호환을 먼저 설계한다.

## 화면 설계

### 데스크톱

1. 공통 shell: 작은 전역 탐색, 작업 제목, 저장 상태, 단계 이동. 대형 hero 제목과 중복 진행 헤더 제거.
2. 작업 입력: 본문 입력과 구조화된 작업 확인. 예시는 선택해서 넣도록 하고 실제 사용자 입력과 섞지 않는다.
3. 위험성평가: 중앙의 읽기 쉬운 표가 기본. 위험요인·현재 조치·추가 조치·담당/기한을 비교하고 선택 행을 편집한다. 열이 많으면 상세 패널로 이동하며, 모든 텍스트를 짧은 카드에 구겨 넣지 않는다.
4. 근거·검토: 선택 행과 연결된 우측 패널. 작업 정보, 오류, 법령/자료 출처를 구분한다. 지속적인 3열은 넓이가 충분할 때만 사용하고 필요 없는 rail은 닫을 수 있다.
5. 내보내기·공유: 좌측에 대상·형식·발송 가능 상태, 중앙에 실제 문서/메시지 미리보기, 필요시 우측 근거·이력. 휴대폰 모형을 기본 작업 화면으로 쓰지 않는다.

### 모바일

- 데스크톱 표를 그대로 축소하지 않는다. 위험 항목 목록 → 선택 항목 편집 → 검토로 연결한다.
- 입력·검토 내용은 읽을 수 있는 크기로 자연스럽게 스크롤한다. 페이지 높이를 강제로 한 화면에 맞추기 위한 다중 내부 스크롤은 금지한다.
- 작업 단위 상단바만 유지한다. 키보드가 열리면 하단 동작이 입력칸을 가리지 않게 처리한다.
- 다음 항목, 이전 항목, 저장 상태가 명확해야 한다. 스와이프만으로 접근 가능한 기능은 두지 않는다.
- 사진과 긴 근거는 명시적인 상세 화면에서 보고 원래 항목으로 돌아온다.

### 스크롤 정책 정정

이전의 '모든 화면을 한 viewport에 넣는다'는 기준을 개편의 최상위 목표로 사용하지 않는다. 첫 화면에서 현재 작업과 주요 행동은 알아볼 수 있어야 하지만, 긴 평가 내용은 충분히 읽고 편집할 공간이 필요하다. 데스크톱 평가표의 단일 명확한 스크롤과 모바일의 자연스러운 페이지 스크롤을 우선한다. 고정 높이·overflow hidden으로 잘린 콘텐츠를 PASS 처리하지 않는다.

## 시각 체계

방향은 **평가표와 검토 결과가 중심인 차분한 실무용 편집 도구**다. 마케팅 페이지처럼 보이거나 경고판처럼 모든 요소가 강조되지 않아야 한다.

- 기존 한국어 글꼴 로딩부터 확인하고 단일 타이포 체계를 적용한다. 본문 16px, 표 14~16px, 보조 13px, 화면 제목 20~24px를 시작안으로 시안에서 검증한다. 자간은 0, viewport 비례 글자 축소 금지.
- 흰색/중립 배경, 짙은 본문, 녹색 주요 행동, 황색 주의, 적색 오류를 의미 기반 토큰으로 정의한다. 밝은 노랑을 보조 버튼 전체에 사용하지 않는다.
- spacing은 4/8/12/16/24/32, 경계 radius는 4~8px. 카드 안 카드와 과도한 그림자 제거.
- 버튼, 입력, 선택, 표, 탭, dialog, drawer, status, error, empty/loading 상태를 동일한 컴포넌트 계약으로 구성한다.
- 기존 아이콘 라이브러리 확인 후 통일. 익숙한 도구는 아이콘+접근 가능한 이름/툴팁, 중요한 제출 동작은 분명한 동사.
- Day/Night 모두 같은 정보 위계와 기능을 유지한다. 대비와 포커스, 확대, 키보드 사용을 검증한다.

## 기능과 상태 설계

각 화면의 정상 화면만 그리지 않는다. 최소한 다음을 함께 확정한다.

| 상태 | 사용자가 알아야 할 내용 | 가능한 다음 행동 |
|---|---|---|
| 빈 작업 | 무엇을 입력하는지 | 입력 또는 원본 선택 |
| 분석 중 | 진행 중인 처리와 입력 보존 | 기다리기/취소 가능한 경우 취소 |
| 서버/AI 미준비 | 사용 불가 이유와 현재 가능한 기능 | 수동 편집 또는 초안 모드 선택 |
| 초안 | AI/템플릿 결과, 미확인 항목 | 작업 정보 확인·수정 |
| 편집 중/저장 중/저장 실패 | 실제 저장 여부 | 재시도·로컬 보존/복구 |
| 원문과 편집본 충돌 | 어떤 내용이 달라졌는지 | 비교·명시적 병합/선택 |
| 검토 필요 | 해당 행의 누락·불일치 | 해당 항목으로 이동 |
| 내보내기 실패 | 형식별 실제 제한 | 가능한 형식 또는 재시도 |

AI 강도는 template/enhanced/full 계약을 유지하되 사용자가 의미와 현재 가용성을 이해하게 표현한다. 자동 검토를 사람 승인이나 법적 충분성으로 표기하지 않는다.

## 구현 구조와 이행

- 공통 shell, 작업 입력/확인, 평가표 편집, 근거 검토, 내보내기 화면을 기능 경계로 나눈다. 단순히 큰 파일을 줄 수 기준으로 나누지 않는다.
- 구조화 위험 행을 편집 정본으로 삼고 원문·첨부·채택 이력은 별도로 보존한다. 내보내기/미리보기/다른 채널은 동일 버전을 사용한다.
- 기존 `runAsk`, 검토 정책, export 계약을 먼저 재사용한다. 화면 개편을 이유로 DB나 제공자를 교체하지 않는다.
- 전역 CSS는 reset/token/shell 등 공통 책임만 남기는 방향으로 전환한다. 새 기능 스타일은 module/component 소유로 제한한다.
- 기능별 전환이 완료될 때 기존 selector/DOM/중복 상태를 함께 제거한다. 새 CSS를 옛 CSS 아래 계속 붙이는 방식은 금지한다.
- 저장 키·기존 문서 형식·공유 링크 호환성을 테스트한다. 정본 변경이 DB migration을 필요로 하면 별도 승인 전 중지한다.

## 실행 단계와 승인점

| 단계 | 산출물 | 다음 단계 조건 |
|---|---|---|
| 0. 현황 고정 | 실제 사용 흐름의 오류 목록, route/state 지도, 현재 화면 캡처, 이전 복구 패치 분리 | 기능 결함과 디자인 부채를 구분 |
| 1. 정보 구조 | 업무 여정, 화면 목록, 데이터/상태 전이, 공통 채널 역할 | 사용자에게 구조를 보여주고 확인 |
| 2. 디자인 시안 | 데스크톱·모바일 입력/평가표/검토·출력 핵심 화면과 오류 상태, 클릭 가능한 prototype | 시각 방향과 주요 흐름 승인; 제품 코드 대규모 변경 전 |
| 3. 디자인 시스템 | 토큰, 폼, 표, 탭, 패널, 상태·오류 컴포넌트와 명세 | 실제 한국어/긴 데이터/좁은 화면 검증 |
| 4. 위험성평가 세로 흐름 구현 | 입력→확인→행 편집→복원→파일 출력의 완결된 한 흐름 | 실제 API와 사용자 수정 데이터로 완주 |
| 5. 보조 화면 이행 | TBM/지원 문서/공유를 새 shell로 전환, 옛 스타일 퇴역 | 새 흐름과 저장본·경로 회귀 검증 |
| 6. 채널 확장 | PWA, MCP/CLI 계약 정렬, 봇 하나의 연동 설계/구현 | 웹 완주와 권한·버전 일관성 확인 후 순차 진행 |
| 7. 배포 검수 | 버전·실제 입력·수정본 출력·시각 검증, 롤백 기준 | staged 공개 후 실제 production 동일 흐름 재확인 |

이번 턴은 계획까지다. 다음 작업은 **제품 코드를 더 덧붙이는 것이 아니라 핵심 화면의 데스크톱·모바일 디자인 시안**이다. 먼저 위험성평가 편집 화면의 방향을 확인하고 입력/검토·출력 화면을 같은 체계로 확장한다.

## 검수 계약

- desktop 1440×900/1440×723, mobile 390×844/390×723에서 Day/Night를 검증한다. 전환 폭 주변과 브라우저 확대, 모바일 키보드도 확인한다.
- 첫 진입, 실제 입력, 생성, 위험 행 수정·추가·삭제, 검토 항목 이동, 새로고침, 중단 복구, 수정본 출력의 연속 동작을 검증한다.
- 단순 성공 응답 대신 입력 작업과 결과의 일치, 수정한 값과 최종 파일의 일치를 확인한다.
- 최소한 조명 교체·운반·화기·화학·굴착 및 정보 부족 입력을 구분한다. 지원하지 않는 경우 다른 업종을 발명하지 않고 확인을 요청한다.
- 수동 텍스트/구조화 편집 충돌, 비로그인·권한 부족·서버 장애·저장 실패·출력 잠금을 포함한다.
- 본문 잘림, 주요 이름 생략, 중복 sticky, 겹침, 잘못된 포커스, 일반 페이지 수평 넘침이 없어야 한다. 표의 의도된 수평 이동은 명시적으로 조작 가능해야 한다.
- 기존 fixture PASS와 실제 saved share 검증은 분리한다. 사용자 실제 작업으로 완주하지 못하면 전체 개편 완료로 보고하지 않는다.

## 범위 통제

사업 확장·다중 봇 동시 출시·네이티브 앱 신규 개발·DB 구조 교체·실제 발송은 본 디자인 단계에서 하지 않는다. 기능 복구, 디자인 시안, 제품 이행, 채널 확장은 각각 별도 변경 묶음과 검증을 갖는다. 기존 기록의 완료 수를 늘리는 일을 사용자 업무 복구보다 우선하지 않는다.

## 현재 판단

버튼 응답 복구는 위험성평가 업무 완료와 다르다. 입력한 작업과 다른 템플릿이 나오거나 생성 직후 행 편집이 잠기면 핵심 기능 실패다. 과거 화면 높이와 샘플 테스트 PASS로 이를 대체하지 않는다.

이번 확인에서 조명 교체가 창고 운반 템플릿으로 선택되고, 생성 후 추가된 검토 설명 때문에 원문/행 동기화 검사가 실패하는 경로를 재현했다. 첫 수정은 작업 우선 판별과 부가 설명을 보존하는 행 편집이다. 모든 업종의 추론, 기존 문서 가져오기, 전체 UI 개편이 완료됐다는 의미는 아니다.

## 사용자가 만나는 흐름

1. 시작: 새 작업 작성 또는 기존 위험성평가 가져오기. 기존 문서는 원본 보존이 먼저다.
2. 작업 확인: 장소·작업·인원·장비·위험을 확인한다. 미입력 정보를 업체명이나 다른 업종의 예시로 채우지 않는다.
3. 평가표: 위험요인, 현재 조치, 추가 조치, 담당자·기한을 한 행 단위로 편집한다. 데스크톱은 표/선택 행, 모바일은 선택 항목 하나의 상세 편집이다.
4. 검토: 누락·불일치와 근거를 해당 행 옆에 보여준다. 자동 검토와 사람 확인을 구분한다.
5. 내보내기: 편집한 정본 그대로 파일을 만든다. 사용할 수 없는 형식과 사용할 수 있는 형식을 분리하고, 저장 실패·내보내기 실패를 숨기지 않는다.

기본 화면에는 입력/평가표/검토·내보내기만 둔다. 지원 문서, 전체 원문, 근거 원문, 자동화 설정은 선택 상세로 둔다. 페이지를 나누는 것만으로는 해결되지 않는다.

## 공통 기능 경계

- 채널마다 독립 생성기·검수기·저장소를 만들지 않는다. 현존 `runAsk`, 구조화 위험 행, 검수 함수를 공통 서비스 계약으로 묶는다.
- 최종 형태는 입력 원본, 확인된 작업 정보, 위험 행, 근거·검토 결과, 버전, 변경 이력의 정본 하나다. 산문과 구조화 행을 각각 고친 뒤 비교하는 방식은 축소한다.
- 가져오기 파서 결과는 후보로 둔다. 원본과 추출 행을 대조하고 사용자가 채택한 뒤 편집 정본으로 전환한다.
- MCP/CLI/봇에서 생성·저장이 자동으로 부수 실행되는 기존 계약은 명시한다. 조회/임시 초안과 저장·발송 승인을 구분한다.
- 토큰 직접 복사보다 사용자 로그인/동의 기반 연결이 최종 목표다. 현재 Bearer 연결을 OAuth 완료로 표현하지 않는다.
- 오프라인 저장은 개인정보 보관 정책·공유 기기·충돌 해결이 함께 정해져야 한다. PWA 설치만으로 오프라인 안전성을 주장하지 않는다.

기술 참고: [PWA 설치](https://web.dev/learn/pwa/installation), [MCP 권한 부여](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

## 완료 기준

- 실제 입력 → 생성/가져오기 → 위험 행 수정 → 행 추가/삭제 → 새로고침 복원 → 수정본 내보내기를 데스크톱/모바일에서 확인한다.
- 시나리오와 무관한 업체·장비·위험을 넣지 않는다. 지원하지 않는 작업은 미확인으로 표시한다.
- 지원 9종·전체 원문은 기본 접힘. 위험성평가가 첫 편집 대상이다.
- 임의 원문 변경 시 조용히 덮어쓰지 않는다. 부가 검토 설명은 구조 편집 후에도 보존한다.
- 서버 출력 잠금은 그대로 유지한다. 로컬 CSV와 브라우저 인쇄는 별도 검증한다.
- DB/발송/공유 세션/벡터/위키/KOSHA registry 변경은 이번 범위 밖이다. exact saved Share는 별도 미증거 상태다.

## 우선순위

현재 위험성평가 한 건 완주 복구 → 검증/표 편집 중심 웹 개편 → 기존 문서 가져오기와 변경 대조 → PWA/이어보기 → 기존 MCP·CLI 계약 정렬 → 고객이 실제 쓰는 봇 한 채널. 다중 채널을 한 번에 출시하지 않는다.
