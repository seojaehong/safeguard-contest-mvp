# Replayed dispatch-log requests create duplicate audit records

## Summary

Dispatch log idempotency key is format-checked but does not prevent replayed audit inserts. Directly reachable through the authenticated product API by replaying the same valid request; the sink records duplicate provider-status/audit rows but does not itself send through a provider.

## Root Cause

The violated invariant is that replayed dispatch-log requests create duplicate audit records. Current source instead shows: POST validates only the key shape, embeds it inside each row's JSON payload, and performs a plain insert; the dispatch_logs schema has no idempotency column or unique constraint, so replaying the same authenticated request creates duplicate provider-status audit records.

## Validation

Method: Static route/schema trace plus existing tenant-boundary test inspection

The authenticated replay path, plain insert, and absence of a unique idempotency column/constraint are explicit in current source.

Limitations:
- No current control queries or reserves the key before insert.
- Live table could have out-of-repo constraints, but live DB evidence is approval-gated and absent.

## Dataflow

Authenticated POST idempotencyKey and dispatch rows -> shape validation and owned workpack check -> key stored only inside JSON payload -> plain dispatch_logs insert without uniqueness or replay reservation.

## Reachability

Directly reachable through the authenticated product API by replaying the same valid request; the sink records duplicate provider-status/audit rows but does not itself send through a provider.

Counterevidence: Authentication, tenant ownership, and preview-only provider capability constrain the effect to operational history; no schema or route control deduplicates the insert.

## Severity

**medium**. The matrix maps medium impact and high likelihood to medium because replay is simple and corrupts dispatch audit truth without proving duplicate external delivery.

Change conditions: Lower or ignore if duplicate rows are proven harmless and excluded from all operational decisions; raise only if the same replay is proven to cause duplicate provider sends or cross-tenant effects.

## Remediation

Add a first-class idempotency key column with a tenant-scoped unique constraint, reserve it atomically before inserting rows, and return the prior result on replay.

Regression tests:
- Replay the same authenticated request twice and assert one logical dispatch-log set.
- Race two requests with the same key and assert one insert wins.
