# Daily entries can reference another tenant's site or workpack

## Summary

daily_entries RLS fails to bind site_id and workpack_id to the owned organization. Browser Supabase clients and canonical owner policies support direct authenticated REST as a distinct path from service-role application access; exploitation requires a valid account and foreign UUID. Live policy/application state is unverified without approval.

## Root Cause

The violated invariant is that daily entries can reference another tenant's site or workpack. Current source instead shows: The policy validates only daily_entries.organization_id, while attacker-selected site_id and workpack_id remain independent foreign keys and can point at another tenant.

### Root Control evidence

`supabase/migrations/003_knowledge_runtime.sql:77-92`

```sql
create policy "owners can manage daily entries"
  on daily_entries for all
  using (
    exists (
      select 1 from organizations
      where organizations.id = daily_entries.organization_id
        and organizations.owner_id = auth.uid()
    )
  )
  with check (
    exists (
      select 1 from organizations
      where organizations.id = daily_entries.organization_id
        and organizations.owner_id = auth.uid()
    )
  );
```

## Validation

Method: Cumulative canonical migration review and static direct-Supabase RLS proof

The current canonical schema ends at migration 010; site_id and workpack_id are independent FKs not checked against row organization_id. No later migration, composite FK, trigger, or policy closes it.

Limitations:

## Dataflow

Authenticated direct Supabase PostgREST write supplies an owned organization_id plus a known foreign site_id/workpack_id UUID -> daily_entries owner policy checks organization_id only -> ordinary FK existence check accepts a cross-tenant relationship -> daily-entry metadata.

## Reachability

Browser Supabase clients and canonical owner policies support direct authenticated REST as a distinct path from service-role application access; exploitation requires a valid account and foreign UUID. Live policy/application state is unverified without approval.

Counterevidence: Service-role application routes often perform stronger ownership checks, but those checks do not govern direct table REST. Foreign-table RLS also prevents claiming direct disclosure of the referenced row, so the proven effect is constrained relationship/provenance integrity.

## Severity

**low**. The matrix maps medium impact and medium likelihood to low because cross-tenant integrity is real in canonical policy but requires authentication, identifier knowledge, and deployed grants/migrations.

Change conditions: Raise if direct REST is live and forged relationships are shown to disclose foreign records or drive privileged export/share/mutation; ignore if verified live constraints or policies enforce same-tenant references.

## Remediation

Require every referenced site and workpack to belong to organization_id in both RLS checks and database constraints or triggers.

Regression tests:
- Tenant A cannot insert or update a daily entry with tenant B site or workpack IDs.
- Valid same-tenant relationships continue to pass.
