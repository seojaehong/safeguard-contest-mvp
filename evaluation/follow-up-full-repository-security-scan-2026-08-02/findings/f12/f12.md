# Read confirmations can bind cross-tenant recipient objects

## Summary

workpack_read_confirmations policy omits same-tenant checks for all related recipient objects. Browser Supabase clients and canonical owner policies support direct authenticated REST as a distinct path from service-role application access; exploitation requires a valid account and foreign UUID. Live policy/application state is unverified without approval.

## Root Cause

The violated invariant is that read confirmations can bind cross-tenant recipient objects. Current source instead shows: workpack_id, share_session_id, worker_id, and site_id are independent FKs, while RLS validates only organization_id; forged confirmation rows can therefore attach to another tenant's identifiers.

## Severity

Change conditions: Raise if direct REST is live and forged relationships are shown to disclose foreign records or drive privileged export/share/mutation; ignore if verified live constraints or policies enforce same-tenant references.

## Remediation

Require session, workpack, site, and worker references to share organization ownership and enforce the expected session-recipient tuple atomically.

Regression tests:
- Reject acknowledgements mixing tenant A and B identifiers.
- Reject workers that are not recipients of the referenced session.
